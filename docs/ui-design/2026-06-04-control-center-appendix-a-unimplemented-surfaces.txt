Appendix A: Unimplemented Control Center Surfaces

A.1. Purpose

В UI Pritha Control Center уже заложены элементы, которые не обязаны быть полностью реализованы в текущей версии Pritha. Это приложение фиксирует, как такие элементы должны вести себя до появления backend-модулей, какие контракты нужно добавить позже и какие действия нельзя имитировать в UI.

Главный принцип:

UI must never pretend that a capability is ready when Pritha cannot verify it.

Любой элемент, который ещё не реализован, должен иметь честный state:

planned
not_installed
disabled
unavailable
pending_auth
manual_only
ready
failed

Это особенно важно для cron/proactivity, Codex limits, app-server telemetry, child-agent start/stop, restore, rollback, phone access, voice tools and update suggestions.

Pritha уже требует readiness-проверки выбранных модулей и явного состояния ready/skipped/failed/pending-auth, а не молчаливого предположения, что модуль готов.  ￼

⸻

A.2. Capability state model

Каждая крупная функция Control Center должна возвращать machine-readable status.

Required status vocabulary

type CapabilityStatus =
  | "ready"
  | "disabled"
  | "manual_only"
  | "planned"
  | "not_installed"
  | "unavailable"
  | "pending_auth"
  | "failed";

UI wording

Status	UI text	Meaning
ready	Ready / Connected	Функция проверена и доступна
disabled	Off	Функция существует, но выключена
manual_only	Manual only	Автоматизации нет, ручной запуск доступен
planned	Planned	UI уже знает о будущей функции, backend ещё не готов
not_installed	Not installed	Нужный adapter/module отсутствует
unavailable	Unavailable	Текущий runtime не даёт такие данные
pending_auth	Needs setup	Нужна авторизация/секрет/разрешение
failed	Failed	Проверка упала, нужна диагностика

UI rule

Не показывать “Connected”, “Ready”, “75% used”, “Cron active”, “Agent running” или похожие состояния без backend-проверки.

⸻

A.3. Cron / Proactivity specification

A.3.1. Product goal

Proactivity в Pritha — это контролируемая способность периодически выполнять проверки, которые помогают Pritha развиваться самой и улучшать child agents.

Будущие proactive задачи:

1. Периодически искать новые материалы для саморазвития Pritha.
2. Определять, какие доверенные ресурсы стоит читать.
3. Проверять child agents на изменения без участия Pritha.
4. Документировать внешние изменения с timestamp/version.
5. Сравнивать новые знания с существующими child agents.
6. Предлагать updates на карточках агентов.
7. Создавать rollback-safe update plan перед изменением агента.

A.3.2. MVP behavior

В MVP cron adapter ещё не реализован.

UI должен показывать:

Proactivity: Off
Manual checks: Available
Cron adapter: Not installed

Допустимые действия MVP:

View planned jobs
Run manual check
Configure draft

Недопустимые действия MVP:

Enable cron
Enable heartbeat
Enable autostart
Install scheduler
Run background polling
Automatically write memory from external sources

Pritha standard уже фиксирует: cron, heartbeat, scheduled jobs, queue watchers, launchd autostart и proactive notifications нельзя добавлять без явного выбора, scheduler owner, schedule policy, memory-write policy, monitoring, kill switch и approval gates.  ￼

A.3.3. Future cron adapter

Cron adapter должен быть не “сырой cron”, а слой Pritha над scheduler.

Pritha Control Center
  -> proactivity manifest
  -> Pritha cron adapter
  -> host scheduler / cron / launchd / external scheduler
  -> run history
  -> reports
  -> update suggestions

Cron adapter должен поддерживать:

status
list jobs
next run
last runs
pause
resume
disable
run-now
dry-run
logs
kill switch

A.3.4. Proactivity job types

Минимальные job types:

type ProactivityJobType =
  | "self_improvement_discovery"
  | "child_agent_drift_audit"
  | "knowledge_to_agent_update_match"
  | "readiness_health_report"
  | "snapshot_retention_cleanup";

1. self_improvement_discovery

Pritha ищет новые материалы, которые могут улучшить:

harness
memory
tools
skills
MCP
UX
voice
evals
safety
operations
child agents

В MVP источники не фиксируем. Позже Pritha должна сама определять, какие ресурсы читать, но source policy должна быть видимой в Dev/Settings.

2. child_agent_drift_audit

Pritha проверяет, изменился ли child agent без её участия.

Примеры сигналов:

AGENTS.md changed
README changed
operations/manifest.json changed
package scripts changed
new files added
known files missing
last readiness changed
URL/port changed
voice module changed

Git не обязателен. Если git есть, можно использовать commit info. Если git нет, использовать fingerprints/checksums/mtime.

3. knowledge_to_agent_update_match

Pritha берёт новые знания и проверяет, каким child agents они подходят.

Результат:

Update suggestion

на карточке агента.

4. readiness_health_report

Периодическая или manual проверка readiness Pritha и child agents.

5. snapshot_retention_cleanup

Удаляет старые snapshots сверх retention policy.

Default retention:

2 snapshots per child agent

A.3.5. Proactivity manifest

Pritha должна иметь manifest или эквивалентный status API.

Рекомендуемый shape:

{
  "version": "0.1",
  "status": "not_installed",
  "mode": "disabled",
  "scheduler_owner": "none",
  "timezone": "Europe/Berlin",
  "jobs": [
    {
      "id": "self-improvement-discovery",
      "type": "self_improvement_discovery",
      "title": "Self-improvement discovery",
      "status": "planned",
      "schedule": null,
      "manual_run": true,
      "writes_memory": false,
      "requires_approval": true,
      "last_run": null,
      "next_run": null
    }
  ]
}

A.3.6. Required job fields

Каждый proactive job должен иметь:

type ProactivityJob = {
  id: string;
  type: ProactivityJobType;
  title: string;
  status: CapabilityStatus;
  mode: "disabled" | "manual" | "scheduled" | "cron" | "heartbeat";
  schedule?: string | null;
  timezone: string;
  source_policy?: string;
  max_runtime_sec: number;
  concurrency: "forbid" | "allow" | "replace" | "queue";
  retry_policy: "none" | "fixed" | "exponential";
  cost_budget?: {
    max_usd?: number;
    max_tokens?: number;
    max_requests?: number;
  };
  memory_write_policy: "none" | "draft_only" | "curated_after_approval";
  approval_required: boolean;
  kill_switch: boolean;
  last_run?: ProactivityRunSummary | null;
  next_run?: string | null;
};

A.3.7. Run history

Каждый manual или scheduled run должен создавать run record.

type ProactivityRunSummary = {
  run_id: string;
  job_id: string;
  trigger: "manual" | "cron" | "system";
  started_at: string;
  finished_at?: string;
  status: "running" | "succeeded" | "failed" | "cancelled";
  duration_ms?: number;
  output_summary?: string;
  report_path?: string;
  update_suggestions_created?: number;
  memory_writes?: number;
};

A.3.8. Safety rules

Cron/proactivity must fail closed.

Rules:

1. No background job writes curated memory directly from raw external input.
2. No hidden source polling writes to child agents.
3. No automatic update application.
4. No cron install without explicit approval.
5. No scheduler without pause/disable/kill switch.
6. No job without max runtime and cost budget.
7. No external source ingestion without untrusted-input policy.
8. No update without snapshot when rollback is expected.

A.5. Child-agent drift audit

A.5.1. Purpose

Drift audit проверяет, развивался ли child agent без участия Pritha.

Сценарий:

Пользователь открыл child agent напрямую в Codex.
Изменил его файлы.
Pritha позже видит изменения.
Pritha документирует observed change.

A.5.2. MVP

В MVP можно сделать manual check.

UI:

Run Manual Audit

Если audit только читает состояние — one-click safe.

Если audit пишет report — confirmation-required.

A.5.3. Drift record

type ChildAgentDriftRecord = {
  agent_id: string;
  detected_at: string;
  detection_method: "mtime" | "fingerprint" | "git" | "manifest" | "healthcheck";
  changed_surfaces: string[];
  summary: string;
  risk_level: "low" | "medium" | "high";
  suggested_version_change?: "none" | "patch" | "minor" | "major";
  report_path?: string;
};

A.5.4. UI behavior

На карточке агента:

Changed outside Pritha

или, если изменения привели к update suggestion:

Review needed

Не смешивать это с Update available. Это разные состояния:

Badge	Meaning
Update available	Pritha предлагает улучшение агенту
Review needed	Агент изменился вне Pritha
Needs check	Health/manifest неясен
Rollback available	Есть snapshot

A.7. Snapshots and rollback

A.7.1. Decision

Rollback uses Pritha-generated snapshots.

Git is optional and not required.

Retention:

2 snapshots per child agent

A.7.2. Snapshot timing

Create snapshot before:

apply update
restore-over-existing-folder
operations manifest migration
voice module migration
settings migration that changes files

Do not create snapshot for read-only checks.

A.7.3. Snapshot contents

Include safe project files needed for rollback.

Examples:

AGENTS.md
README.md
docs/
interfaces/
operations/
scripts/
package.json
manifest files
selected config templates

Exclude:

.env
.env.local
secrets
tokens
credentials
node_modules
.venv
.memory/*.sqlite
.memory-private
.queue
.logs
runtime state
large media
cache

A.8. Restore for missing agents

A.8.1. Source of restore

Restore does not restore a full archive from memory.

Restore source:

lifecycle reports
selected modules
Pritha registry
known operations metadata

Pritha registry is already the historical view of known agents, but physical liveness must be checked by folder scan.  ￼

A.8.2. Restore flow

Missing card
  -> Restore
  -> Restore plan
  -> Final confirmation
  -> Rebuild sibling folder
  -> Run readiness check
  -> Write recovery report
  -> Card becomes alive

A.8.3. Restore plan shape

type RestorePlan = {
  agent_id: string;
  agent_name: string;
  target_folder: string;
  source_contract: string;
  source_reports: string[];
  selected_modules: string[];
  expected_url?: string;
  risks: string[];
  will_create_folder: boolean;
  will_overwrite_existing_folder: false;
};

If target folder already exists, this is not missing-agent restore. It becomes repair/migration and requires a separate flow.

A.22. Summary

This appendix turns UI placeholders into explicit future modules.

MVP rule:

Show the shape of the future Control Center, but only enable actions that Pritha can verify and perform safely today.

Cron/proactivity is planned but disabled until adapter, run history, source policy, memory-write policy, approval gates and kill switch exist. Child-agent management can start with registry + folder scan + operations manifest. Voice can start as a compact mobile-first control surface with narrow tools and explicit decisions. Developer page remains read-only.
