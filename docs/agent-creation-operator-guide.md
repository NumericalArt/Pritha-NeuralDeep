# Создание агента в Pritha NeuralDeep: инструкция оператора

Эта инструкция описывает исправленный протокол новых задач. Его действующий выпуск и результаты проверок перечислены в [журнале реализации](agent-creation-reliability.md). Исторические задачи сохраняют закреплённый executor и прежние правила; обновление приложения не переводит их автоматически на новый протокол.

## Нормальный путь

1. В Settings → NeuralDeep проверить доступность ключа и выбранную модель. Ключ вводится только в локальную форму. Модель и лимиты времени закрепляются при создании задачи; последующее изменение Settings действует на новые задачи.
2. Создать задачу «Создание агента», указать цель, пример ожидаемого результата и предел токенов. Preflight проверяет чистоту исходников и доступность точного выпуска до платного шага. Не устранять предупреждение копированием состояния другого экземпляра.
3. Ответить на вопросы. Проверить контракт, затем отдельно Outcome Spec. Контракт определяет устройство, Outcome Spec — результат и проверки. Просмотр документа сам по себе не является подтверждением. Codex-оператор указывает основание поручения; это не финальная приёмка пользователем.
4. Если предложение неверно, выбрать «Пересмотреть предложение» и записать полную поправку. История и прежние approvals сохраняются; новая ревизия требует новых подтверждений. После создания проекта пересмотр задания оформляется отдельной задачей и каталогом.
5. Исследование проверяет только выбранные возможности. Хост сохраняет Search/Read первоисточников, модель выбирает точные выдержки. Неподтверждённая тема остаётся блокером. Наличие Voice, RAG или OpenAI в старом примере не делает их обязательными для текстового продукта.
6. После реализации дождаться проверок и демонстрации. «Готов к демонстрации» не означает «принят пользователем». Проверить видимый результат и отдельно выполнить operator Trials.

## Что делать после обрыва

Сначала открыть ту же задачу и обновить состояние. Перезагрузка страницы не создаёт новый job и не является командой повторить inference. Если ответ на нажатие потерян, кнопка «Проверить сохранённое действие» повторяет исходный request ID, ревизию и полномочия.

| Действие | Что происходит | Что оно не доказывает |
|---|---|---|
| Сверить расход | Читаются сохранённые квитанции этой задачи | Потерянный final usage не восстанавливается догадкой; unknown может сохраниться |
| Проверить сохранённую работу | Проверяется уже существующий кандидат; новые команды разрешены только для доказанно изолированных Trials без сети | Это не новая реализация и не приёмка продукта |
| Завершить перенос проверенного результата | Хост переносит точный чистый commit, для которого проверки актуальны и исходная версия не изменилась | Не устраняет неизвестный расход и не закрывает operator Trials |
| Продолжить создание | Может запускать новый платный шаг из оставшегося бюджета после допуска | Не увеличивает лимиты, не очищает unknown и не сбрасывает счётчики |
| Приостановить / отменить | Останавливается дальнейшее выполнение с сохранением истории и кандидата | Это не удаление результата и не возврат потраченных токенов |

Если дерево процессов ещё не завершилось, повторное выполнение недоступно. Если продукт, Outcome, approvals или locked verifier изменились, прежних проверок недостаточно для переноса. Не редактировать SQL, receipts и protected документы ради разблокировки. Не запускать случайные новые попытки до первого успеха.

## Как читать расходы и настройки

- Подтверждённый итог относится к закрытым шагам. Нижняя граница дополнительно включает измеренные запросы незавершённого шага; повторно складывать их нельзя. Cached input уже входит в input.
- Pending означает, что запрос ещё выполняется. Unknown после остановки означает отсутствие достоверного итога. Ноль в подтверждённой части не означает отсутствие расхода.
- Резерв — консервативное ограничение допуска, а не счёт провайдера. Размер контекста в КиБ измеряет UTF-8 байты. Эти единицы не равны токенам.
- Общий prompt budget чата не заменяет лимиты подготовки: 64 КиБ начальный запрос, 96 КиБ граница checkpoint, 128 КиБ жёсткий предел; до 12 запросов. Подготовка получает до 30% бюджета с отдельными долями brief/research, 70% защищены для реализации. Дополнительные запросы могут быть отклонены раньше, если полного резерва не хватает.
- Для Qwen 3.8/3.6 настройка effort не применяется. Это не выключает thinking. Noreason — отдельный model ID, выбираемый явно. Profile v2 задаёт предел ответа 16384 для Qwen с thinking, 8192 для остальных моделей. Старые задачи сохраняют закреплённый предел. Общая квота и квоты фаз не увеличиваются. Документация провайдера не заменяет испытания tools/schema на выбранной модели.
- «Ответ достиг предела выходных токенов» отличается от переполнения входного контекста и ошибки вложения. Без пригодного ответа задача останавливается, расход сохраняется. Повтор с теми же параметрами может снова потратить квоту без результата. Отсутствие отдельного счётчика reasoning в квитанции не доказывает, что thinking был выключен.
- Новая итерация ограничена выбранным временем Settings (не более 30 минут). Запрос получает окно внутри оставшегося времени и отдельный запас на завершение и учёт. После soft deadline новый запрос не отправляется, чтобы не обрывать его через несколько секунд. Старые jobs сохраняют старые сроки.

## Что сохранить для расследования

Сохранить job ID, версии исходников/runtime/executor, точный blocker, время остановки, request/launcher IDs, этап, confirmed/minimum/unknown/reserved usage и ссылки на checkpoint/Trials. Использовать instance-local audit/reports, не Git source и не чат с секретами. Не очищать историю и не менять закреплённую модель во время сравнения.

Реальный контрольный corpus должен заранее фиксировать задания, число повторов, model/release/budget. Детерминированные тесты транспорта доказывают обработку сбоя, но не качество реального ответа. До реальных повторов нельзя обещать устойчивое создание одним проходом.

## Если исследование остановилось на источнике

Во время получения источников карточка показывает «Pritha выполняет подготовку
текущего шага». В этот момент «Продолжить» и пересмотр предложения недоступны:
работа уже выполняется. Можно приостановить или отменить её; обновление страницы
не начинает новый запрос. Состояние кнопок учитывает активную операцию хоста,
даже если запрос к модели ещё не отправлен.

Новые задачи сохраняют первичные страницы и каждую попытку отдельно. Известный
официальный адрес читается сразу; для остальных нужен релевантный Search result.
Пустая прочитанная страница может привести к одной ограниченной попытке другого
источника. Это остаётся в пределах двух attempts на тему. Ошибка доступа или
неподтверждённая операция автоматически не повторяется.

После сообщения «обе попытки исчерпаны» очередное «Продолжить» не добавит попытку.
Нужно исправить техническое предложение штатным пересмотром с новыми approvals
либо передать сохранённый blocker разработчику. Не изменять research/SQLite и
не создавать заменяющие задания ради успешной статистики. Старые jobs сохраняют
свою policy и release; исправление источников действует на новые jobs.
